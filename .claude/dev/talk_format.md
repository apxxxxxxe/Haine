# トークの書式・表示仕様

トークを書くときの技術仕様。旧 `talk-guide` スキル（2026-07-02 廃止）の基礎情報節から、エンジン仕様に当たる部分だけを退避したもの。口調・表現パターンは `.claude/skills/haine-mimicry/references/expression-basics.md` にある。

## 表示速度とリズムの制約

伺かではトークのテキストが**1文字あたり50msで順次表示**される。小説と異なり、**読者は表示が完了するまで次の段落を読めない**。

### translate.rs による自動ウェイト付加

`translate.rs` は以下の記号・タグに自動でウェイトを挿入する。トーク執筆時はこれらの累積コストを意識すること。

| 記号 / タグ | 付加ウェイト | 備考 |
|---|---|---|
| 1文字 | +50ms | balloonwait 設定値 |
| `、` | +600ms | |
| `。` | +1200ms | scope 0（ハイネ）では句点自体が消えウェイトのみ残る |
| `？` | +1200ms | |
| `！` | +1200ms | |
| `…` | +600ms | quicksection 内で処理される |
| `」` | +600ms | |
| `』` | +600ms | |
| `\\n\\n[half]`（連続） | +700ms | `\\n` 単体にはウェイトなし |

`φ`（PHI文字）はエスケープとして機能し、直前の記号へのウェイト付加を抑制する（早口トークで使用）。

**コスト計算例**：「目が合った。少し間があった。」
- 「目が合った。」= 6文字×50ms + 1200ms = **1500ms**
- 「少し間があった。」= 8文字×50ms + 1200ms = **1600ms**
- 合計 **3100ms**（約3秒）——「間を表現する文」は文字コストと句点コストを二重消費する

### この制約から導かれる原則

バルーン（吹き出し）は最後の文字が表示されてから30秒で強制的に閉じる。**全文字が表示されてから1秒以内にトークの意図が読み解けるレベルの明瞭さが必要**（意図的に伏せた情報は除く）。

- **即時把握可能な明瞭さ**: 全文表示後1秒で「何を言いたかったか」が分かること。不確定要素（感情・意図の解釈余地）と、意図そのものの不明瞭さは別物
- **一読で通らない書き方の禁止（再読不可）**: 読み手はバルーンを読み返せない。よく読めば意味が通る＝失敗。トークは論理パズルではない。次の失敗署名を自己点検で潰す——①**逆転ロジック**（技術的には読めるが既定の解釈と逆。例「扉は開けてあるのに戻ってくる」＝開いているなら戻るのは順当、と読める）②**主語欠落**（動作の主語が一読で確定しない）③**技巧的な冗長**（凝った言い換え。意味が取れる最小の言い回しにする）
- **読点の乱用を避ける**: 読点が多いとリズムが刻まれすぎて意味が取りづらくなる。文法上必要な箇所と、間として効かせたい箇所だけに絞る
- **情報密度の維持**: 1文字ごとに情報・感情・驚きのいずれかが前進していること。停滞する文は待機時間になる
- **不要な記述の極限カット**: 視線の移動、行動の説明、感情の注釈など、サーフェスコードや文脈から自明な情報はすべて削除対象
- **「間を表現する文」の禁止**: 「少し間があった。」「一拍の間。」等の文は文字コスト＋句点コストを二重消費する。間の演出はサーフェスコードの切り替えか `\\_w[]` に任せ、地の文で記述しない
- **リズムの設計**: `\\n`・`\\n\\n[half]`・`\\_w[]`・句読点による間は単なる区切りでなくタイミング制御。密度を落とさず情緒を作るために使う
- **長さの自己正当化**: 行数が多いことは正当化理由にならない。7〜10行の目安は「密度が維持できる上限」であり、5行でも密度が高ければ十分

## 全体長の目安（必須の自己点検）

**テンポと密度はトレードオフではなく、テンポを優先する**。描写を細密化すると臨場感は上がるが、その対価としてテンポが失われる。本プロジェクトは一貫して**テンポを臨場感より優先**する方針で設計されている。

| 指標 | 下端（短くて十分） | 上限（これを超えたら肥大化） | 明確な超過 |
|---|---|---|---|
| 本文行数 | **6〜8 行** | **10〜13 行** | 15 行超 |
| `\\n\\n[half]` 区切りビート数 | **3** | **5** | 6 以上 |
| `\\1` 連続単独ビート | 最大 1 | 最大 2 | 3 以上 |

**重要**: 上の表の「下端」は最低ラインではなく**短くて十分**という意味である。10〜13 行は**標準ではなく上限**であり、多くのトーク（特に WithYou のハプニング系）は **6〜10 行**で成立する。writer は「標準」を目指して膨らませるのではなく、「下端で足りないか」を先に検討する。

**ベンチマーク品質の実例**:

| トーク名 | 行数 | ビート数 | 備考 |
|---|---|---|---|
| 「ページを切る」 | 約 10 | 3 | 本の栞切りの典型的な短尺成功例 |
| 「封蝋を捺す」 | 11 | 4 | 構え→儀式→構え解除＋観察眼の強着地 |
| 「湿ったマッチ」手本 | **6** | **3** | ハプニング系の極短尺成功例 |
| 「取れたボタン」 | 約 13 | 4 | 上限ライン上の成功例 |
| 「食事中の読書」 | 約 10 | 3 | |

上記いずれも**上限以下**に収束している。新規生成時は「下端（6〜8 行）で成立するか？」を先に問い、成立しないと確認してから行数を足す。

**肥大化の主因（writer の陥りやすい罠）**:
- 物理プロセスを律儀に全工程描写してしまう（「棒を傾ける→艶を持つ→雫が落ちる→指先に跳ねる→こすり落とす→印章を握る→押し当てる→離す→紋章が残る→余り粒」のように連続して並べる）
- **診断過程の描写**: ハイネが何かを「確認」する過程（振る・嗅ぐ・触る・観察する）を律儀に並べる。結論が明らかなら全て省略すべき
- マイクロ動作の挿入（「親指で」「半歩」「じわりと」「すかさず」「側薬に滑らせる」等の微細修飾）
- interleave のために足した台詞が、実態は細密描写の合間の繋ぎに過ぎない
- **クッション表現の単独行化**（「ねえ、悪いのだけれど。」を独立行にする → 本題と同行に結合すべき）

**書き終わった後の自己点検**: 本文行数を数え、**下端（6〜8 行）まで削れないか**を必ず試す。「書き終えた」時点での行数を基準にするのではなく、「この半分に削れないか？」を自問する。加筆ではなく削除で調整する。残す基準は「この一行が無いとトークの核が成立しないか？」であり、「あると臨場感が増すか？」ではない。

## 書式とマークアップ

- **表情コード**: `h1111210`など7桁数字でハイネの表情・ポーズを制御
  - **7桁構成**: `h[1000000][100000][10000][1000][100][10][1]`

  | 桁 | 意味 | 値 |
  |---|---|---|
  | 1000000 | 特殊 | 基本的に1 |
  | 100000 | 顔色 | 1:通常、2:赤面 |
  | 10000 | 眉毛 | 1:通常、2:困り眉、3:怒り眉 |
  | 1000 | 腕のポーズ | 1:手を前で組む、2:両手を胸に当てる、3:腕を組んで右手を顎にあてる |
  | 100 | 口の形 | 1:無表情、2:閉じ笑い、3:歯を見せた笑い |
  | 10,1 | 目 | 1:こっち開き目、2:下向き開き目、3:あっち開き目、4:こっち半眼、5:下向き半眼、6:あっち半眼、7:こっちほぼ閉じ目、8:下向きほぼ閉じ目、9:あっちほぼ閉じ目、10:閉じ目、11:笑い目 |

  - **例**: `h1111210`（1-1-1-1-2-10）= 特殊1-通常顔色-通常眉-手を前で組む-閉じ笑い-閉じ目
- **`\\1`開始トークの初期サーフェス**: `\\1`で始まるトークでも冒頭にhコードを置いてハイネの初期表情を設定する（例：`h1111110\\1本棚の本が……`）。省略するとサーフェスが未定義になる
- **改行**: `\\n`で文の区切り、`\\n\\n`で話題の区切り
- **1行の文字数制限**: セリフ描画領域は1行最大23文字。`\\n`による改行は23文字に収まらない場合にのみ使う。短い文を不必要に改行で分割しない
- **間**: `\\_w[数字]`で発言の間を作る（重要な発言前によく使用）
- **自動ウェイト**: `\\n\\n[half]`は`translate.rs`でウェイトが自動追加されるため、それだけで十分な間が生まれる。「一拍の間。」「沈黙。」等の尺取り描写は冗長であり不要。間はマークアップに任せ、地の文では描写や行動に集中する
- **沈黙行の禁止**: 「……。」のみの単独行で沈黙を表現しない。間が必要ならサーフェスコード変化（例: h1111210→h1111205）で表情遷移を挟むことで代替する。サーフェスコード変化自体が「間」として機能する
- **アンカー**: `\\_a[AnchorTalk,ID,ユーザの反応]\\_a`で派生話題への導線。ランダムトークとアンカートークは1対1。既存ID: "Misemono", "Poltergeist", "LikeTheGranma", "LiveHome", "NoblesseOblige"。新規アンカーには新IDと対応アンカートークの実装が必要。アンカー作成要件：リンク文字列から自然に続く補足内容、クリックする価値のある情報、知識のひけらかしにならない自然さ
